# HRNeo — конфигурация и CLI

Справочник по параметрам конфигурационного файла `hrneo.conf`, CLI-флагам и формату вспомогательных файлов (`domain.conf`, `ip.list`).

**Версия кода:** hrneo 3.21.0-1le2 (форк le0nus; пакет `1:3.21.0-1le2`)

---

## Запуск

```bash
hrneo [OPTIONS]
```

Все параметры конфигурационного файла можно передать флагами при запуске.

**Приоритет:** `флаги командной строки` > `конфигурационный файл` > `встроенные значения по умолчанию`.

Флаги можно указывать частично — недостающие значения берутся из конфигурационного файла или дефолтов.

---

## Служебные флаги

| Флаг | Назначение |
|------|------------|
| `--version`, `-v` | Вывести версию и выйти |
| `--help`, `-h` | Вывести справку по флагам и выйти |
| `--config <path>` | Путь к конфигурационному файлу |
| `--genconfig [path]` | Создать файл конфигурации со всеми параметрами по умолчанию и выйти |
| `--keenetic <token>` | Записать токен доступа Keenetic (`rciToken`) в конфиг и выйти |
| `--match <имя>` | Спросить работающий демон, к какой цели относится имя, и выйти |
| `--dump` | Вывести watchlist работающего демона и выйти |
| `--raw-off` | При остановленном демоне удалить переходы и цепочку `HRNEO_GUARD`; при занятой блокировке выйти с кодом 2 без удаления |

### `--config <path>`

- по умолчанию: `/opt/etc/HydraRoute/hrneo.conf`
- если указан явно и файл недоступен — ошибка и выход
- если путь по умолчанию недоступен — продолжение с дефолтами + флаги

### `--genconfig [path]`

Поведение по аргументу:

- **без аргумента** — `hrneo.conf` рядом с исполняемым файлом (каталог бинарника, не дефолтный путь)
- **аргумент-каталог** (или со слешем) — `<dir>/hrneo.conf`
- **аргумент-файл** — записать ровно по этому пути

Ключи с пустым дефолтом пишутся как `ForceInterface=`, `GeoIPFile=`, `GeoSiteFile=`, `PolicyOrder=`, `l7WanInterface=`, `rciToken=`.

### `--keenetic <token>`

Записывает токен доступа Keenetic в ключ `rciToken` целевого конфига (`--config <path>` либо дефолтный `/opt/etc/HydraRoute/hrneo.conf`) и завершает работу, не запуская демон. Остальные ключи, комментарии и порядок строк сохраняются (запись через временный файл + `rename`).

Поведение по текущему значению `rciToken` в файле:

- ключ отсутствует **или** пустой → токен добавляется — `Keenetic token added`;
- ключ есть и отличается → перезаписывается на месте — `Keenetic token updated`;
- ключ есть и совпадает → файл не трогается — `already set, unchanged`;
- пустой/битый токен (пробелы, управляющие, не-ASCII, длиннее 511) → `invalid Keenetic token`, выход 1;
- ошибка чтения/записи файла → выход 1.

Пример: `/opt/bin/hrneo --keenetic SQ1DJN5YI4mfYLsgVjI9or5qKCh1gV5dUNCqwkW5T7HNd8VXwBUWOoCe`

### `--raw-off`

Служебный режим: конфиг не читается, демон не запускается. Работает только при остановленном демоне: пытается взять эксклюзивную неблокирующую блокировку `/var/run/hrneo.lock` (её весь срок жизни держит работающий hrneo); при занятой блокировке печатает `hrneo is running; stop it first (neo stop)`, выходит с кодом 2 и ничего не удаляет. Иначе удаляет переходы и цепочку `HRNEO_GUARD` в `raw` обоих семейств и записывает `raw_guard=off` в файл статуса. Коды выхода: `0` — защита снята, статус `off` записан; `1` — ошибка удаления правил (приоритетнее `3`); `2` — демон держит блокировку, ничего не удалено; `3` — правила удалены, но файл статуса не записан (повторный вызов публикует `off` и даёт `0`). Обычно вызывается как `neo raw-off` — см. «Защита от утечек».

### `--match <имя>`, `--dump`

Клиент watchlist API: подключается к сокету `/var/run/hrneo.sock` работающего демона, выводит ответ и завершается. Конфиг не читается, демон не запускается.

- `--match <имя>` — строка `OK <цель> <ранг> <ключ>` или `NO`; выход 0 — имя в watchlist, 1 — нет, 2 — ошибка или демон не запущен.
- `--dump` — весь watchlist: строки `T <ранг> <цель>`, `K <ключ> <ранг>`, в конце `END <n>`; выход 0 — выгрузка получена полностью, 2 — ошибка.

Пример: `/opt/bin/hrneo --match www.youtube.com`. Протокол и порядок работы для сторонних программ — `docs/WATCHLIST_API.md`.

> Все параметры имеют встроенное значение по умолчанию (см. колонку «default» в `--help`). Отсутствие любого ключа в конфиге **ИЛИ** среди флагов → используется дефолт (включая строковые пути `watchlistPath` / `CIDRfile` / `logfile` / `log`). Невалидное числовое значение ключа в конфиге (нечисловое, число с мусором, ≤0 для строго положительных) → `[WARN] Invalid <key> value` + дефолт; у булевых ключей любое значение, кроме `true`, трактуется как `false`. Невалидное значение **CLI-флага** — ошибка и выход с кодом 1. Падения при отсутствии ключей нет.

## Доступ к RCI Keenetic

### `rciToken=`

Токен доступа Keenetic для авторизации запросов к RCI роутера (`http://127.0.0.1:79/rci`). По умолчанию пусто.

**Заполнять вручную не нужно.** При старте hrneo сам проверяет, требует ли прошивка токен, и если требует, а в конфиге токена нет или он отклонён — выпускает новый через `ndmc` (`authentication token generate HydraRoute`) и записывает сюда. Свои прежние токены (метка `HydraRoute`) при этом удаляются, чужие не трогаются. Хранится в `hrneo.conf` — общий с hrweb ключ; hrweb только читает его и показывает в разделе «Настройки», где значение можно задать руками, если нужен токен, выпущенный в веб-панели роутера (**Управление → Токены доступа**).

Режим работы определяется пробой `GET /rci/show/version`, а не наличием значения:

| Проба с токеном | без токена | Поведение |
|---|---|---|
| — (токена нет) | 200 | токен не нужен, заголовок не шлётся |
| — (токена нет) | 401/403 | токен выпускается через `ndmc` |
| 200 | — | `X-NDMA-TKN` на каждом запросе |
| 401/403 | 200 | токен отклонён, работа продолжается без него, в лог — предупреждение |
| 401/403 | 401/403 | токен перевыпускается через `ndmc` |

Недопустимые символы (пробелы, управляющие, не-ASCII) обрезают токен при загрузке — защита от инъекции в HTTP-заголовок; факт обрезки пишется в лог.

## Основные параметры

### `autoStart=true`

Разрешить запуск программы.

- если `false` — программа немедленно завершается после чтения конфига, `iptables` и `ipset` не трогаются
- используется init-скриптом `S99hrneo` для управления запуском без изменения конфига

### `watchlistPath=/opt/etc/HydraRoute/domain.conf`

Путь к файлу с доменами и политиками.

- формат строки: `domain1,domain2,geosite:TAG/ПолитикаИлиИнтерфейс`
- любой домен (например, `youtube.com`) → точное совпадение и автоматический суффиксный матч всех его поддоменов; режима «только точное совпадение» нет
- ведущая точка не нормализуется: `.youtube.com` не совпадёт ни с одним именем — домены писать без точки
- `geosite:TAG` — загружает домены из GeoSite-файла для данного тега
- несколько geosite-тегов и обычные домены можно смешивать в одной строке в любом порядке
- если цель (после `/`) совпадает с именем сетевого интерфейса — используется DirectRoute, иначе — политика Keenetic
- строки, начинающиеся с `#` или `##`, являются комментариями
- длина строки не ограничена: список из тысяч доменов через запятую одной строкой обрабатывается целиком (чтение через `getline`)
- DNS-запросы перехватываются у клиентов на интерфейсах любого типа, включая VPN-клиентов роутера (WireGuard / VPN-сервер / IPsec / туннели), а не только LAN

### `clearIPSet=true`

Очищать содержимое `ipset` при запуске — **только при `KeepIpsetOnRestart=false`**.

- `true` при `KeepIpsetOnRestart=false` — при старте все `ipset`-множества программы сбрасываются (`flush`), CIDR и DNS-кэш теряются; flush очищает записи, но не пересоздаёт существующий сет и не меняет его CREATE-параметры
- при `KeepIpsetOnRestart=true` (по умолчанию) не действует: сеты сохраняются, в журнал (уровень INFO) пишется `clearIPSet=true: ipsets kept, KeepIpsetOnRestart=true (neo ipset-clean empties them)`; очистить вручную — `neo ipset-clean`
- `false` — сохранять накопленные IP между перезапусками; не совместимо с изменением таймаута `ipset`

## CIDR

### `CIDR=true`

Включить поддержку статических IP/подсетей.

- при включении читается `CIDRfile` и все записи загружаются в `ipset` при старте
- одиночный IP с маской `/32` или `/128` добавляется как хост, иначе как подсеть

### `CIDRfile=/opt/etc/HydraRoute/ip.list`

Путь к файлу с CIDR-записями.

- формат секции: `/ПолитикаИлиИнтерфейс` (заголовок), далее IP/CIDR построчно
- `#/ПолитикаИлиИнтерфейс` — отключённая секция, содержимое игнорируется
- `##` — комментарий
- директива `geoip:CC` внутри секции — загружает CIDR для страны из GeoIP-файлов
- пустая строка завершает текущую секцию
- длина строки не ограничена (чтение через `getline`)

### `GeoIPFile=`

Путь к файлу базы GeoIP в формате v2ray/xray `.dat`. Параметр повторяемый:

```
GeoIPFile=/opt/etc/x-ui/bin/geoip_RU.dat
GeoIPFile=/opt/etc/x-ui/bin/geoip.dat
```

- используется совместно с директивой `geoip:cc` в файле `ip.list` (например `geoip:ru`, `geoip:cn`)
- при обработке директивы программа обходит все указанные файлы и собирает CIDR из каждого
- файлы читаются потоково без кэширования, в памяти хранятся только извлечённые CIDR-записи
- поиск тега в файле выполняется полным сканированием независимо от порядка записей в файле
- если параметр не задан, директивы `geoip:` в `ip.list` игнорируются с предупреждением `[WARN] GeoIP directive 'geoip:CC' found but GeoIPFile not configured`; пустое значение (`GeoIPFile=`, как пишет `--genconfig`) равносильно отсутствию ключа
- если ни один файл не содержит запрошенного кода, выводится предупреждение `[WARN]`
- GeoIP-диаппазоны загружаются однократно при старте; `SIGUSR1` их не перечитывает

## GeoSite

### `GeoSiteFile=`

Путь к файлу базы GeoSite в формате v2ray/xray `.dat`. Параметр повторяемый:

```
GeoSiteFile=/opt/etc/HydraRoute/geosite.dat
GeoSiteFile=/opt/etc/x-ui/bin/geosite.dat
```

- используется совместно с директивой `geosite:TAG` в файле `domain.conf` (например `geosite:google`)
- при обработке программа обходит все указанные файлы и объединяет домены из каждого
- файлы читаются потоково без кэширования, в памяти хранятся только извлечённые домены
- поиск тега в файле выполняется полным сканированием независимо от порядка записей в файле
- поддерживаются типы доменов: **Domain** и **Full** — оба вставляются как записи `domain.conf` (точное совпадение + суффиксный матч поддоменов)
- типы **Plain** (keyword-матч) и **Regex** не поддерживаются — пропускаются с предупреждением `[WARN]`
- запись `domain.conf` имеет приоритет над GeoSite: если домен присутствует в обоих источниках, используется политика из `domain.conf`
- если параметр не задан, директивы `geosite:` в `domain.conf` игнорируются с предупреждением на каждую: `[WARN] GeoSite directive 'geosite:TAG' found but GeoSiteFile not configured`; пустое значение (`GeoSiteFile=`, как пишет `--genconfig`) равносильно отсутствию ключа
- если ни один файл не содержит запрошенного тега, выводится предупреждение `[WARN]`
- GeoSite-домены загружаются однократно при старте; `SIGUSR1` их не перечитывает

## IPSet

### `IpsetEnableTimeout=true`

Включить автоматическое удаление записей по таймауту.

- `true` — `ipset`-множества создаются с поддержкой timeout; записи удаляются по истечении `IpsetTimeout`
- `false` — записи хранятся до явной очистки или перезагрузки роутера; обычный рестарт при `KeepIpsetOnRestart=true` их сохраняет
- `clearIPSet` действует только при `KeepIpsetOnRestart=false`; flush очищает записи, но не пересоздаёт существующий сет и не меняет его CREATE-параметры. Изменение поддержки timeout или параметров создания требует контролируемого пересоздания сетов при остановленном hrneo (`neo raw-off`, затем `ipset destroy` нужных сетов: пока цепочка `raw` стоит, сет занят и не удаляется)

### `IpsetTimeout=21600`

Таймаут записей в секундах (применяется только при `IpsetEnableTimeout=true`).

- `21600` = 6 часов, `86400` = 24 часа
- таймаут отсчитывается от **последнего** DNS-ответа (или L7-совпадения) с этим IP: повторное добавление существующего IP продлевает запись ещё на `IpsetTimeout`
- записи из `ip.list` и `geoip:` добавляются без таймаута и остаются постоянными, даже если тот же IP приходит в DNS-ответах

### `IpsetMaxElem=262144`

Максимальное количество записей в одном `ipset`-множестве.

- дефолт hrneo — `262144` (у ядра по умолчанию 65536); передаётся в `ipset CREATE` как атрибут `IPSET_ATTR_MAXELEM`
- значение задаёт жёсткий лимит на каждое `ipset`-множество; IP сверх лимита не добавляются (kernel вернёт `IPSET_ERR_HASH_FULL` → `[WARN]`)
- применяется при `CREATE` нового сета; существующий сет не пересоздаётся ни рестартом, ни `clearIPSet`, поэтому изменение лимита требует того же контролируемого пересоздания сетов при остановленном hrneo (см. `IpsetEnableTimeout`)
- управляет двумя механизмами защиты ipset от переполнения с общим подсчётом записей: **автомиграция** — `geoip:TAG` с числом записей больше `IpsetMaxElem − 5000` (запас `CIDR_MIGRATE_HEADROOM`) отключается переносом в `#/Too-big-geoip-tag` в `ip.list` (атомарная перезапись через `.tmp + rename`) с `[WARN]`; **лимит загрузки** — суммарное число записей в каждом `ipset` не превышает `IpsetMaxElem`, теги/записи сверх лимита пропускаются с `[WARN]`

## Логирование

### `log=off`

Режим логирования (дефолт `off` — отладочные уровни отключены, но `[WARN]`/`[ERROR]` идут в системный лог).

| Значение | Поведение |
|----------|-----------|
| `console` | весь вывод в `stdout` процесса, включая `[DEBUG]`-сообщения |
| `file` | запись в файл `logfile`, включая `[DEBUG]`-сообщения |
| `syslog` | отправка через `openlog`/`vsyslog` в `LOG_DAEMON` с тегом `"hrneo"`; `logfile` игнорируется |
| `off` или иное | отладочные уровни (`[DEBUG]`/`[INFO]`/`[MATCH]`/`[PROCESSED]`/`[FILTERED]`) отключены; `[WARN]`/`[ERROR]` направляются в системный лог (`openlog`/`vsyslog`, `LOG_DAEMON`, тег `"hrneo"`) — чтобы критичные сообщения не терялись в `stderr` демона |

**Уровни логов:**

- `[DEBUG]` — детали операций
- `[INFO]` — штатные события
- `[MATCH]` — совпадение домена
- `[PROCESSED]` — добавление IP в ipset
- `[FILTERED]` — отклонение служебного IP
- `[WARN]` — некритичные проблемы
- `[ERROR]` — ошибки

### `logfile=/opt/var/log/LOGhrneo.log`

Путь к файлу логов.

- используется только при `log=file`; при пустом значении логирование отключается
- директория создаётся автоматически если не существует
- файл открывается в режиме `append`; старые записи не удаляются

## Direct Routing

### `DirectRouteEnabled=true`

Включить прямую маршрутизацию трафика на сетевые интерфейсы.

- при старте программа сканирует `/sys/class/net/` и строит список доступных интерфейсов; скан однократный — `SIGUSR1` список не обновляет
- если цель в `domain.conf` (`ip.list`, `geosite:`-правиле) совпадает с именем интерфейса — настраивается `ip rule + ip route` для данного интерфейса; иначе цель считается политикой Keenetic. Исключение — цели из `ForceInterface`: политикой они не считаются никогда
- интерфейс, появившийся после старта, hrneo не замечает: его цель остаётся тем, чем её классифицировали на старте, до перезапуска (`neo restart`)
- если интерфейс DOWN при старте — создаётся `blackhole`-маршрут; при изменении состояния интерфейса маршрут обновляется по сигналу `SIGUSR1`
- `false` — все цели в `domain.conf` считаются политиками Keenetic, DirectRoute не настраивается

### `InterfaceFwMarkStart=12289`

Начальный `fwmark` для интерфейсов (`0x3001`).

- каждому интерфейсу назначается уникальный `fwmark` начиная с этого значения
- используется в правилах `iptables CONNMARK` и `ip rule fwmark`

### `InterfaceTableStart=301`

Начальный номер таблицы маршрутизации для интерфейсов.

- каждому интерфейсу назначается уникальная таблица начиная с этого номера
- в таблице создаётся маршрут `default via <шлюз> dev <интерфейс>` (шлюз берётся из per-interface таблиц NDMS; у туннелей без шлюза — `default dev <интерфейс>`) или `blackhole default`

### `ForceInterface=awgmX,t2sX,opkgtun2`

Цели, которые всегда считаются интерфейсами, даже если на момент старта их нет в `/sys/class/net/`. По умолчанию пусто.

Нужно для интерфейсов, которые сторонняя программа (awg-manager, opkg-туннели, tun2socks и т.п.) создаёт позже hrneo. Без параметра такая цель на старте классифицируется как политика Keenetic: hrneo создаёт в конфигурации NDMS пустую политику с этим именем и сохраняет конфигурацию, а при каждой следующей загрузке роутера, если hrneo снова стартует раньше интерфейса, — создаёт её заново.

#### Синтаксис

- значение — список через запятую, пробелы вокруг запятых обрезаются, до `MAX_INTERFACES=64` элементов
- `X` (заглавная) на конце — любой непустой цифровой индекс: `awgmX` совпадает с `awgm0`, `awgm12`, но не с `awgm`, `awgm1a`, `awgmX`
- без `X` на конце — точное имя: `opkgtun2` совпадает только с `opkgtun2`
- интерфейс, имя которого само оканчивается на `X`, указать нельзя — запись всегда читается как шаблон
- регистр значим: имена сравниваются как есть

#### Поведение на старте

Для каждой цели из `domain.conf`, заголовков `/Имя` в `CIDRfile` и `geosite:`-правил:

| Цель | Есть в `/sys/class/net/` | Результат |
|------|--------------------------|-----------|
| совпала с `ForceInterface` | да | обычная цель-интерфейс DirectRoute (как без параметра) |
| совпала с `ForceInterface` | нет | цель исключается целиком |
| не совпала | да | обычная цель-интерфейс DirectRoute |
| не совпала | нет | политика Keenetic |

Исключённая цель не оставляет следов:

- строки `domain.conf` с этой целью пропускаются вместе со всеми доменами — их нет в таблице доменов, DNS- и L7-ответы по ним ничего не добавляют, watchlist API отвечает `NO` (`hrneo --match <домен>`)
- `geosite:`-правила с этой целью отбрасываются; блок `CIDRfile` с этим заголовком не загружается, потому что ipset для цели не создаётся (загрузчик пропускает блоки без ipset). Если в ядре остался одноимённый ipset от прошлых запусков, блок попадёт в него — на маршрутизацию это не влияет, CONNMARK-правил на этот ipset нет
- не создаются политика Keenetic (в RCI цель не уходит), ipset-пара, `fwmark`/таблица, `ip rule`/`ip route`, CONNMARK-правила
- `fwmark` и номер таблицы не расходуются: их получают только присутствующие интерфейсы, по порядку. Когда исключённый интерфейс появится и hrneo перезапустится, номера у интерфейсных целей могут сдвинуться — правила при старте всё равно ставятся заново

#### Лог

Строка на каждое вхождение цели — отдельно для `domain.conf`, `CIDRfile` и `geosite:` (цель из всех трёх источников даст три строки):

```
[INFO] Interface awgm7 not present (ForceInterface=awgmX), target skipped
[DEBUG] CIDR block start: awgm7 (skipped - no ipsets exist)
```

В `Target order (N)` исключённой цели нет. Если она указана в `PolicyOrder`, сортировка её пропускает с обычным предупреждением `[WARN] PolicyOrder: policy 'awgm7' not found, skipping`.

#### Порядок работы со сторонней программой

1. В `hrneo.conf` прописать шаблоны интерфейсов программы: `ForceInterface=awgmX`.
2. В `domain.conf`/`ip.list` указывать системное имя интерфейса как цель: `youtube.com/awgm0`.
3. Программа, подняв свои интерфейсы, перезапускает hrneo (`neo restart`). `SIGUSR1` для этого не подходит: он не пересканирует `/sys/class/net/` и не переклассифицирует цели.

Интерфейс, пропавший после старта, hrneo тоже не отслеживает: правила и таблица остаются до перезапуска.

#### Чего параметр не делает

- не удаляет пустые политики, созданные hrneo до появления параметра. Удаляются один раз вручную: `no ip policy awgm0`, затем `system configuration save`
- без `DirectRouteEnabled=true` не действует: интерфейсных целей нет вообще, все цели — политики

## Conntrack

### `ConntrackFlush=true`

Сбрасывать соединения `conntrack` при первом добавлении IP в `ipset`. Флаг управляет обоими каналами (DNS и L7), но механизм сброса у них разный.

- `true` (по умолчанию):
  - **DNS-канал** — при первом добавлении IP (`NLM_F_EXCL` вернул `err=0`) IP кладётся в pending-буфер (`conntrack_flush_request`), а netlink-DUMP `conntrack`-таблицы выполняется **асинхронно**: DUMP-сокет неблокирующий и зарегистрирован в главном epoll, чанки таблицы читаются между DNS-пакетами, `DELETE` отправляется для каждой записи с dst-IP из pending. Обработка DNS никогда не ждёт сканирования таблицы (при burst-резолвах — загрузка страницы — ipset add всех доменов завершается сразу, один DUMP обслуживает весь burst). Это нужно, чтобы уже установленное соединение к этому IP получило новый `fwmark` при следующем пакете и ушло через нужный туннель/интерфейс
  - **L7-канал** (TLS-SNI / HTTP-Host / QUIC-SNI) — при первом добавлении IP удаляет **одну** conntrack-запись триггернувшего соединения точечно по полному 5-tuple (TCP, для QUIC — UDP) (`conntrack_delete_conn`, без DUMP таблицы, без коллатерали для чужих соединений к тому же IP). L7 ловит ClientHello уже установленного соединения, поэтому запись всегда существует и удаляется
- фактический сброс происходит **ТОЛЬКО** при одновременном выполнении условий:
  1. `ConntrackFlush=true`
  2. IP добавлен в `ipset` впервые (повторное добавление того же IP новым не считается — `NLM_F_EXCL` → `IPSET_ERR_EXIST`; оно только продлевает таймаут)
  3. (DNS) существует активная `conntrack`-запись с `dst==этот IP`; для L7 это условие выполняется по построению

  Для DNS, если соединения к IP ещё нет — DUMP проходит вхолостую, DELETE не отправляется.
- `false` — не выполнять `conntrack`-сброс **ни на одном канале**; соединения, установленные ДО добавления IP в `ipset`, продолжат идти с прежним `fwmark` до переподключения. Для L7 это означает, что трафик к свежеопознанному хосту останется в обход политики до реконнекта приложением
- ранее L7-канал вместо conntrack использовал инъекцию TCP RST (`l7_rst.c`), не зависевшую от `ConntrackFlush`. Механизм удалён: spoof-RST как in-band-пакет проигрывал гонку seq-окна (RFC 5961) и на практике не рвал соединение. Теперь L7 использует надёжный conntrack-DELETE, единообразно подчинённый флагу `ConntrackFlush`
- `fork/exec` не используется — всё через прямые netlink-сокеты (`NETLINK_NETFILTER`, long-lived, открыты один раз при старте): неблокирующий сокет под DUMP-поток (в epoll) и отдельный под `DELETE` fire-and-forget (без `NLM_F_ACK`). Разделение сокетов исключает рассинхрон чтения ответа из недочитанного DUMP; `SO_RCVBUF` DUMP-сокета поднят до 1 МБ против переполнения на больших таблицах

## Порядок правил и приоритет политик

### `PolicyOrder=HydraRoute,RU,CN`

Единый управляемый приоритет политик/интерфейсов hrneo. Решает коллизии маршрутизации, когда один и тот же IP или один и тот же домен попадает сразу в несколько целей (политик и/или DirectRoute-интерфейсов) watchlist'а.

#### Синтаксис

- значение — список имён через запятую (имена политик Keenetic и имена сетевых интерфейсов одинаково; hrneo их различает автоматически через `drm_classify_target` по `/sys/class/net` и `ForceInterface`)
- пробелы вокруг запятых обрезаются (`trim_whitespace`)
- до `MAX_POLICY_ORDER=64` элементов
- если параметр отсутствует или пустой — все цели сортируются строго алфавитно

#### Правила сортировки (`sort_policies`)

- цели из `PolicyOrder` выстраиваются в указанном порядке первыми
- остальные цели (есть в watchlist/CIDRfile/geosite, но нет в `PolicyOrder`) добавляются после них алфавитно (`qsort`)
- цели из `PolicyOrder`, отсутствующие во всех источниках (watchlist + CIDRfile + geosite-правила) — пропускаются с предупреждением:

  ```
  [WARN] PolicyOrder: policy 'X' not found, skipping
  ```

- полный порядок печатается в лог при старте:

  ```
  [INFO] Target order (N):
    [0] HydraRoute (policy)
    [1] nwg0 (interface, fwmark=0xNNNN)
    ...
  ```

#### Где порядок реально применяется (ДВА независимых уровня)

**1) Порядок правил `iptables/mangle/PREROUTING`**

hrneo проходит по итоговому отсортированному массиву `g_all_sorted[]` и добавляет правила `mangle` по набору на цель (R0–R3 для политики, R1–R3 для интерфейса) — в порядке массива. `iptables-restore --noflush` сохраняет этот порядок при apply. Поскольку iptables проверяет правила сверху вниз и берёт **первое** совпадение, при попадании пакета в несколько `ipset` одновременно (например, IP сразу в `HydraRoute` и в `RU`) победит та цель, чьё правило добавлено раньше — то есть стоящая раньше в `PolicyOrder`. Это справедливо для mangle сама по себе; при `RawGuard=true` выбор складывается из двух уровней.

**Выбор при `RawGuard=true`.** Среди политик первой в `PolicyOrder` побеждает та, что стоит раньше (в `raw` правила идут в обратном порядке, последнее совпадение — первая политика — задаёт метку). Но метка политики выставляется уже в `raw`, а при `GlobalRouting=false` R1 цели-интерфейса пропускает пакет с меткой `0xffffaaX`, и пакет с connmark 0 фиксирует R0 политики. Пример: адрес входит и в ipset цели-интерфейса `nwg0` (DirectRoute), и в ipset политики `HydraRoute`, `nwg0` стоит в `PolicyOrder` раньше. При умолчаниях (`RawGuard=true`, `GlobalRouting=false`) новое соединение уйдёт через политику `HydraRoute`, а не через `nwg0`. Правило «первой побеждает цель выше в `PolicyOrder`» для связки интерфейс/политика действует при `RawGuard=false` и при `GlobalRouting=true`. В режиме `degraded` результат зависит от правил `raw` и `mangle`, фактически действующих в семействе: при обычном сбое установленная цепочка `raw` сохраняется (например, при ошибке дампа mangle IPv6 уцелевшая цепочка IPv4 продолжает ставить метку политики), и политика по-прежнему может иметь приоритет.

**2) Выбор политики при матчинге домена**

При резолве DNS-ответа или L7-имени hrneo ищет домен в хеш-таблице и обходит все суффиксы; если один домен присутствует в нескольких целях (например, в watchlist прописано):

```
google.com/HydraRoute       # родитель
mail.google.com/RU          # поддомен в другой политике
```

или CNAME-цепочка проходит через домены разных политик — выигрывает цель, стоящая раньше в том же итоговом порядке, что и правила CONNMARK: сначала `PolicyOrder`, затем остальные по алфавиту. Длина совпавшего суффикса и позиция домена в CNAME-цепочке на выбор не влияют: без `PolicyOrder` в примере выше `mail.google.com` уйдёт в `HydraRoute`, а домен из цели, стоящей раньше, выигрывает у CDN-имени из цели ниже (например, из geosite), где бы в цепочке они ни стояли. То есть `PolicyOrder` влияет и на **выбор** ipset для конкретного DNS-ответа, а не только на порядок правил.

#### Чего `PolicyOrder` не решает

- **Политика, привязанная к устройству в настройках роутера, стоит выше.** `ndm` маркирует такой трафик до правил hrneo, и условие `-m mark ! --mark 0xffffaa0/0xffffff0` заставляет hrneo уступить целиком, независимо от порядка. Снимается только `GlobalRouting=true`
- **Уже установленные соединения не пересматриваются.** Guard `-m connmark --mark 0x0/0xffffffff` пропускает только непромаркированные соединения, поэтому цель фиксируется на соединении один раз. Соединение, ушедшее в другую цель до того, как IP попал в нужный `ipset`, доживает там до истечения conntrack-записи; переключение на лету даёт `ConntrackFlush=true`

#### Практически

Положите в начало `PolicyOrder` те политики, в которые надо направлять трафик при коллизиях (например, узкие/более специфичные туннели), а оставшиеся (общие, fallback) — в конце или вне списка.

#### Обновление при SIGUSR1

- `SIGUSR1` **НЕ** перечитывает `hrneo.conf` и сам `PolicyOrder`; `apply_unified_connmark_rules` приводит mangle и raw к точному ожидаемому содержимому и порядку в текущем порядке `g_all_sorted[]`; замена нужна при любом расхождении, не только при отсутствии правил. При расхождении в семействе все правила hrneo этого семейства пересоздаются одним `iptables-restore` в порядке `PolicyOrder` — дописывание через `-A` поставило бы цель ниже остальных
- для применения нового `PolicyOrder` нужен перезапуск (`neo restart`)

## Защита от утечек (raw guard)

### `RawGuard=true`

Ранняя маркировка трафика целей-политик в таблице `raw` (цепочка `HRNEO_GUARD`). Устройство — `CORE.md`, раздел 8 В.

- `true` (по умолчанию; так же, если ключа в конфиге нет — переписывание конфига из hrweb защиту не выключит) — пакеты к адресам из списков получают метку политики до conntrack и mangle, поэтому пересборка iptables силами NDMS (продление DHCP, смена WAN), перезапуск и падение hrneo не отправляют их в WAN; при лежащем туннеле их дропает правило NDMS `blackhole` политики
- `false` — после чтения конфига и применения CLI, до необязательной инициализации и ранних выходов, hrneo удаляет существующий raw guard; правила остаются только в mangle, как до защиты. Статус `off` публикуется только после подтверждения отсутствия цепочки и переходов в обоих семействах; ошибка или частичное удаление дают `degraded:raw-off-failed-v4|v6` и WARN
- только цели-политики Keenetic (IPv4 и IPv6); цели-интерфейсы DirectRoute не затрагиваются
- уже установленный raw guard при обычном сбое сохраняется (остановка, рестарт и падение hrneo цепочку не снимают); вручную — `neo raw-off`. Единственное аварийное исключение: если в mangle остался безусловный `CONNMARK --restore-mark`, установлен переход в `HRNEO_GUARD`, а замена mangle на R0–R3 не удалась, hrneo одним `iptables-restore` удаляет переходы в `HRNEO_GUARD`, очищает цепочку и выставляет `degraded:old-restore`. Это предотвращает постоянное обнуление ранней метки новых соединений старым R2
- `degraded` означает, что защищённое состояние не подтверждено; гарантия не действует. Журнал: `[WARN] raw guard degraded: <причина>-v4|v6`, при восстановлении `[WARN] raw guard on again (was degraded: …)`; строка `raw_guard=degraded:<причина>-v4|v6` в файле статуса
- порядок установки: сначала mangle в обоих семействах, потом raw; цепочка не ставится, пока набор mangle не подтверждён, не известны метки политик (кроме целей с подтверждённым `ABSENT`: полный 404 или пустая метка `""`; они исключены из правил и монитора, и `raw_guard=on` не подтверждает их покрытие, пока метка не получена снова: по `SIGUSR1` или перепроверкой раз в 60 с) или остался безусловный restore
- с `GlobalRouting=false` сохраняется приоритет назначенной устройству политики Keenetic; подробности — в разделе `GlobalRouting`
- **перед переходом на версию hrneo без этой защиты** (откат, `opkg install --force-downgrade`): `neo stop` → успешный `neo raw-off` → даунгрейд. При ошибке остановки или удаления защиту не считать снятой и даунгрейд не продолжать: старые правила mangle вместе с оставшейся цепочкой отправляют каждое новое соединение в WAN. Для обычного обновления на версию с защитой этого не требуется

### `KeepIpsetOnRestart=true`

Не очищать ipset при старте, даже при `clearIPSet=true`.

- `true` (по умолчанию) — записи переживают перезапуск hrneo (обновление geo, `neo restart` из AWG Manager), защита `raw` работает сразу после старта; DNS-записи доживают свой `IpsetTimeout`, постоянные записи, убранные из `ip.list`, остаются до перезагрузки роутера или `neo ipset-clean` (а от ближайшего подходящего DNS-ответа с этим адресом становятся временными)
- `false` — `clearIPSet` действует как раньше
- повторное добавление известного адреса — продление, а не «новый IP», поэтому `ConntrackFlush` соединения не рвёт
- устаревшие DNS-записи после смены списков живут до `IpsetTimeout`; для немедленной очистки — `neo ipset-clean`
- если CIDR-список при старте не удалось прочитать целиком (кроме отсутствующего файла: он считается пустым), `geoip.dat` повреждён или результат добавления постоянной записи неизвестен (ответ ядра потерян или запрос не отправлен), для затронутых сетов продление существующих записей отключается до рестарта: постоянный хост иначе получил бы `IpsetTimeout`. Один `[WARN] permanent-host index incomplete for <сет>: refresh disabled` на сет; новые DNS-адреса добавляются как обычно

### `BlockedLogDelay=30`

Сколько секунд политика может оставаться без пути, прежде чем в журнал попадёт `[WARN] guard: policy <X> blocked`.

- путь проверяется каждые 10 с: в таблице правила NDMS `fwmark <метка> lookup <таблица>` должен быть unicast-маршрут по умолчанию через интерфейс (наличие пути, а не здоровье туннеля)
- монитор работает синхронно с общим дедлайном 200 мс на весь раунд, а не на семейство или запрос: превышение даёт `unknown`, следующий тик пропускается; ошибка создания или регистрации таймера даёт WARN и `unknown`
- IPv6 учитывается, только если в `main` есть default-маршрут (любого вида, blackhole и unreachable тоже); при его подтверждённом отсутствии — `n/a`; итог — худшее из учитываемых семейств
- после этого WARN возврат пути пишет `[WARN] guard: policy <X> restored after <N> s` (тоже WARN, поэтому видно и при `log=off`)
- ошибка запроса к ядру — `unknown`: не считается ни путём, ни его отсутствием; `unknown` не завершает и не начинает заново уже открытый эпизод `blocked` (его начальное время сохраняется), эпизод сбрасывается при подтверждённом `ok` или `n/a`

### Файл статуса `/var/run/hrneo-status`

tmpfs; пишется атомарно (`rename`) и только при изменении. Интерфейс для внешних служб статуса и уведомлений:

```
raw_guard=on|off|degraded:<причина>
raw_rules_v4=<n>|unknown
raw_rules_v6=<n>|unknown
policy.<X>.v4=ok|blocked:<unix-time>|unknown|n/a
policy.<X>.v6=ok|blocked:<unix-time>|unknown|n/a
last_rebuild=<unix-time>
```

Счётчики отражают наблюдаемое число правил `HRNEO_GUARD` по последнему успешному дампу, а не желаемое; при неудачном дампе значение — `unknown`.

Причины `degraded` (с суффиксом семейства `-v4`/`-v6`): `raw-modules` (таблицы `raw` нет в ядре), `no-mark` (метка политики неизвестна), `old-restore` (остался безусловный restore), `dump` (не прочитан дамп), `batch-overflow`, `restore` (`iptables-restore` не прошёл), `audit` (повторный дамп не совпал), `conntrack-module` (`xt_conntrack` не загружается), `raw-off-failed` (`RawGuard=false`, снятие не подтверждено). После остановки hrneo файл остаётся со старым содержимым — живость процесса проверяется по `/var/run/hrneo.pid`; `hrneo --raw-off` записывает в него `raw_guard=off`.

### `neo raw-off`, `neo ipset-clean`

- `neo raw-off` останавливает hrneo, до 10 с ожидает фактического завершения процесса и освобождения `/var/run/hrneo.lock`, затем вызывает `hrneo --raw-off`. Если остановка не подтверждена, команда завершается с ошибкой (код 1) без удаления raw guard. hrneo остаётся остановленным; следующий обычный старт с `RawGuard=true` снова включает защиту, насовсем — `RawGuard=false`
- `hrneo --raw-off` работает только при остановленном демоне: пытается взять эксклюзивную неблокирующую блокировку того же файла; при занятой блокировке печатает `hrneo is running; stop it first (neo stop)`, выходит с кодом 2 и ничего не удаляет. Коды выхода (их же возвращает `neo raw-off`): `0` — защита снята, статус `off` записан; `1` — ошибка удаления правил (приоритетнее `3`) либо не взята блокировка; `2` — демон держит блокировку; `3` — правила удалены, но файл статуса не записан (повторный вызов публикует `off` и даёт `0`)
- `neo ipset-clean` выполняет `stop` → подтверждение завершения процесса → `start` с `--KeepIpsetOnRestart false --clearIPSet true`. Если старый процесс не завершился, команда выходит с ошибкой без запуска нового. Переход и цепочка raw сохраняются. Постоянные адреса восстанавливаются загрузкой списков; DNS-адреса — последующими DNS-ответами. Адреса, отсутствующие в ipset после очистки, до повторного добавления не защищены
- при удалении пакета `prerm` действует только на `remove`: остановка, `hrneo --raw-off`, проверка пустоты `raw` каждого семейства, выгрузка модулей `raw` только после успешного дампа без правил, пользовательских цепочек и нестандартных политик. При `upgrade <версия>` он ничего не делает; код `3` — предупреждение, остальные ошибки оставляют пакет на месте

### Чего защита не покрывает

Первые пакеты после свежего DNS-ответа до добавления адреса в ipset; окно загрузки роутера до старта Entware/hrneo; `GlobalRouting=true` в окно пересборки NDMS; политики, разрешающие WAN; цели-интерфейсы DirectRoute; соединения с ненулевой connmark другой цели или старой меткой; ответы входящих соединений к внешним адресам из списков в окно отсутствия R3, включая связанные ICMP-ошибки (`RELATED_REPLY`); режим `degraded`; адреса, истёкшие в ipset по `IpsetTimeout`, пока клиент использует свой DNS-кэш; весь переход пересоздания политики от исчезновения старого правила NDMS до установки новых правил hrneo, включая новые соединения, и старые соединения со старой connmark до закрытия; постоянный хост, удалённый из `ip.list`, который сохраняется после рестарта, но при следующем подходящем DNS-ответе становится временным.

Защита не затрагивает собственный `OUTPUT` роутера, адреса вне списков и устройства с назначенными политиками при `GlobalRouting=false`.

## Глобальная маршрутизация

### `GlobalRouting=false`

Режим обработки политик роутера.

- `false` (по умолчанию) — уважать существующие политики роутера (`NoVPN`, `Policy0` и т.д.); правила HydraRoute/интерфейсов применяются только к пакетам без установленной политики; устройства с назначенными политиками роутера сохраняют свою маршрутизацию
- `true` — перезаписывать все политики роутера; правила применяются ко всем пакетам независимо от их политик роутера
- с `RawGuard=true` при `GlobalRouting=false` сохраняется приоритет назначенной устройству политики Keenetic; условие R1 не перезаписывает такую политику. R0 фиксирует метку `raw` только при совпадении текущей метки пакета с меткой цели. При `GlobalRouting=true` в окно пересборки NDMS метки политик устройств могут взять верх над hrneo; этот случай вне гарантии
- перед включением защиты на роутере проверьте её взаимодействие с политиками, назначенными устройствам в NDMS

## Взаимодействие с роутером через RCI

**RCI** (Remote Configuration Interface) Keenetic.

Вся штатная работа идёт через собственный минимальный HTTP/JSON-клиент к локальному эндпойнту `ndmsv` (TCP `127.0.0.1:79`), реализованный внутри бинаря. `ndmq`, `curl`, `wget`, `jq`, `python` не вызываются никогда.

Единственное исключение — `ndmc`: он используется **только** как канал бутстрапа токена доступа на прошивках KeeneticOS 5.2+, где RCI требует авторизации (`ndmc` остаётся без авторизации). Подробности — в разделе про `rciToken`.

Это значит:

- нулевые runtime-зависимости от userspace утилит роутера на штатном пути
- никаких `fork`/`exec` на каждое обращение → меньше latency и пиков CPU
- статическая сборка остаётся самодостаточной; конфигурация роутера читается и изменяется напрямую через netlink-подобный по простоте JSON API
- параметра конфига для RCI нет — endpoint захардкожен (`127.0.0.1:79` — стандартный порт RCI на всех современных прошивках Keenetic v3+)

### Что hrneo делает через RCI

**1. Создание отсутствующих политик доступа (при старте)**

Для всех уникальных политик из watchlist + CIDRfile + geosite-правил hrneo формирует JSON-массив команд:

```http
POST /rci/ HTTP/1.0
Content-Type: application/json

[{"ip":{"policy":{"HydraRoute":{"description":"HydraRoute"}}}},
 {"ip":{"policy":{"RU":{"description":"RU"}}}},
 {"ip":{"policy":{"CN":{"description":"CN"}}}},
 {"system":{"configuration":{"save":true}}}]
```

- description политики выставляется равным её имени — WebUI Keenetic показывает description, и по нему ищут политику сторонние пакеты (например, nfqws2-keenetic); сам hrneo работает только с именем
- если политика уже существует — меняется только её description
- если политики нет — создаётся пустая (без VPN-интерфейсов; их присваивает администратор вручную через веб-интерфейс Keenetic → Приоритеты подключений → Политики доступа или через HRWeb)
- команда `save` (эквивалент `system configuration save` — запись в startup-config роутера) идёт **последним элементом того же массива**, одним POST-запросом вместе с командами создания политик (формат `/rci/` поддерживает смешанные батчи)
- Лог: `[INFO] Policy creation commands executed`
- Имена политик с интерфейсами не смешиваются: цели, классифицированные `drm_classify_target` как сетевые интерфейсы (DirectRoute), в RCI не отправляются — для них правила маршрутизации настраиваются через `ip rule + ip route`, а не через политики Keenetic. Цели из `ForceInterface`, интерфейса которых на старте нет, тоже не отправляются — они исключены целиком

**2. Получение `markID` политики (на стартовой сверке и для целей без правил)**

Точечный запрос:

```http
GET /rci/show/ip/policy/HydraRoute/mark HTTP/1.0
```

Ответ — голое значение (`"ffffaaa"`, ~10 байт); полный HTTP 404 = политики нет, явно пустая метка `""` = `markID` ещё не назначен.

- полное дерево `/rci/show/ip/policy/` (JSON со всеми маршрутами всех политик, растёт без ограничений) **не выкачивается**; из ответа снимаются кавычки и префикс `0x` (хранится как строка для прямой подстановки в `iptables --set-xmark 0xNN`)
- вложенные show-пути работают только прямым GET — в батч-POST ndm их не поддерживает (проверено на Keenetic 5.0.12: `1179781`)
- Лог при `log=console/file`: `[DEBUG] RCI policy: HydraRoute mark=0xffffaaa`
- `markID` используется в правилах `CONNMARK` (mangle) и `MARK` (`raw`, цепочка `HRNEO_GUARD`) для связи `ipset` → политика
- когда запрашивается: RCI запрашивается для всех целей-политик на стартовой сверке до первого успешного коммита; далее — при неизвестной метке или подтверждённом отсутствии подходящего правила NDMS в дампе `ip rule`. Ошибка дампа не считается отсутствием правила. Политика с подтверждённым `ABSENT` запрашивается снова только по `SIGUSR1` и раз в 60 с. Если метка известна и правило NDMS на месте, цель пропускается без сетевых вызовов (обоснование — `docs/MARKID_DRIFT.md`)
- смена метки политики обнаруживается по дампу `ip rule` (rtnetlink, строгий разбор): профиль правила NDMS — `fwmark <метка>` с полной маской и `lookup <таблица>`; новая метка пишет `[WARN] Policy X mark changed: 0x… -> 0x…, replacing its rules`, пропавшее правило — `[WARN] Policy X: no ip rule for fwmark 0x…, reading its mark again`

**3. Retry-логика markID**

- `rci_get_policy_mark` не ретраит и не спит: `1` — марк получен, `0` — политики нет или `markID` ещё не назначен (только полный HTTP 404 или явно пустая метка `""`), `-1` — транспортная ошибка (любой другой статус, оборванный или нечитаемый ответ), `-2` — авторизация отклонена (401/403)
- `-1` и `-2` (ответа нет) делают `apply_unified_connmark_rules` возвращающим `-1`; повтор обеспечивает коммитер netfilter в `main.c` (`commit_run`: первая пауза 50 мс, дальше 100, 250, 500, 1000 мс и затем каждые 3 с, без ограничения числа попыток; успех или новый `SIGUSR1` начинает снова с 50 мс)
- `0` (подтверждённый ABSENT) коммит не роняет: повторы каждые 3 с не вернули бы политику, а только повторяли бы запрос RCI и дампы таблиц. Такую политику запрашивает первый коммит после каждого `SIGUSR1` и медленная перепроверка раз в 60 с (на таймере монитора, без дампов); коммит следует, только если метка вернулась или RCI не ответил. Политика, пересозданная без события NDMS, и политика, только что созданная hrneo при старте, пока Keenetic не назначил ей `markID`, получают правила в пределах 60 с
- для политики формируются R0–R3, для интерфейса — R1–R3. TRANSPORT/DENIED сохраняют известную метку и существующие правила; только подтверждённый ABSENT разрешает удаление правил цели. Неизвестная с самого старта метка сохраняет существующие строки, но препятствует подтверждению raw guard
- при сбое получения марки пишется `[WARN]` (`RCI unreachable while reading policy X`, `RCI denied reading policy X`, `Policy X has no mark ID yet`) — один раз на цель и причину, повторы той же причины пишутся как `[DEBUG]`; `ipset` продолжает заполняться. `TRANSPORT`/`DENIED` сохраняют известную метку и существующие правила цели; метка, неизвестная с самого старта, сохраняет существующие строки, но трафик цели не получает новых правил и raw guard не подтверждается (`degraded:no-mark`). Остальные цели применяются в том же батче
- `0` (подтверждённый ABSENT: политики нет) — уже стоящие правила этой цели удаляются как осиротевшие (из mangle и raw): её `markID` Keenetic выдаст следующей созданной политике; состояние raw guard и статус определяют остальные цели

**4. Сетевые параметры**

- TCP к `127.0.0.1:79` (`INADDR_LOOPBACK`), `SO_RCVTIMEO`/`SO_SNDTIMEO` = `RCI_TIMEOUT_SEC=10` секунд (для send и recv отдельно)
- HTTP/1.0 (`Connection: close` по умолчанию — каждый запрос = новый TCP-сокет, ответ читается до EOF)
- Заголовки формируются вручную через `snprintf`; блок заголовков разбирается строго (статусная строка `HTTP/1.x NNN`, строки оканчиваются CRLF, `Content-Length` либо тело до закрытия соединения, любой `Transfer-Encoding` — ошибка), оборванный или нечитаемый ответ — транспортная ошибка; затем код: 200 — успех, 401/403 — отказ авторизации, прочие — HTTP-ошибка
- клиент **без состояния и без `malloc`**: приёмный буфер — статический `RCI_RAW_MAX=32 КБ` в `rci_request` (ответы точечных GET — десятки байт). Прежние heap-буферы по ~1 МБ (`rci_client_init`/`rci_client_close`) под выкачивание полного дерева политик удалены вместе с ручным JSON-парсером (`find_matching_brace` + `strstr "mark"`)

### Системные требования

- демон запущен от root (доступ к `loopback:79` + локальной аутентификации NDM, которая для root прозрачна)
- RCI на роутере включён (на всех современных прошивках Keenetic — да, по умолчанию слушает `127.0.0.1:79` для управления через веб-интерфейс и системные утилиты)

## Сигналы управления

### `SIGUSR1`

Обновить правила `iptables` и состояние интерфейсов без перезапуска.

- приводит правила hrneo в `mangle/PREROUTING` (R0–R3) и цепочку `raw` `HRNEO_GUARD` к точному ожидаемому тексту и порядку на текущей конфигурации в памяти (config, watchlist и GeoSite не перечитываются); замена нужна при любом расхождении, не только при отсутствии правил; по дампу `ip rule` проверяет, не пересоздана ли политика; повторно запрашивает RCI о политиках с подтверждённым `ABSENT`
- обновляет состояние интерфейсов (`up`/`down`) для DirectRoute и корректирует маршруты; список интерфейсов не пересканирует — интерфейс, появившийся после старта, подхватывается только перезапуском (см. `ForceInterface`)
- если `l7CaptureEnabled=true` и L7-перехват успешно стартовал — дописывает недостающие `NFLOG`-правила (TCP 80/443, при `l7EnableQUIC` ещё UDP/443) на WAN-интерфейс в `mangle/FORWARD`+`OUTPUT`; при `l7CaptureEnabled=false` шаг пропускается. Правила hrneo (CONNMARK + L7 NFLOG) пишутся одной командой `iptables-restore --noflush` на семью; что уже стоит, определяется по дампу только разбираемых цепочек (`mangle -S PREROUTING`, при L7 ещё `-S FORWARD`/`-S OUTPUT`, при `RawGuard` — `raw -S`) — вызовов `iptables -C` нет. Если всё на месте, `iptables-restore` не запускается
- **каждый сигнал** выполняет запись **немедленно**; подтверждающая — через `NF_VERIFY_INTERVAL_MS` = 250 мс после последнего сигнала, неудачная запись повторяется через 50 мс с ростом паузы до 3 с. Коалесцирования нет: каждый хук пачки (~30 на одно событие) сверяет дамп цепочек, а `iptables-restore` запускается, только если правила отличаются от ожидаемых. Каждый хук стоит дампов mangle и raw, дампа `ip rule` и, если правила политики нет или политика отсутствует (`ABSENT`), запроса RCI
- отправляется автоматически хуками `/opt/etc/ndm/netfilter.d/015-hrneo.sh` (Keenetic переписал таблицы netfilter) и `/opt/etc/ndm/ifstatechanged.d/015-hrneo.sh` (сменилось состояние интерфейса)

### `SIGTERM` / `SIGINT`

Штатная остановка:

- останавливается поток watchlist API, сокет `/var/run/hrneo.sock` удаляется
- снимаются L7 `NFLOG`-правила (если были установлены)
- удаляются `ip rule` и `ip route` для DirectRoute-интерфейсов
- удаляются правила hrneo в `mangle` (одним `iptables-restore` на семейство); цепочка `raw` `HRNEO_GUARD` **остаётся** (защита на время рестарта и после падения), ipset не очищается
- закрываются netlink-сокеты (`ipset`, `conntrack`, `NFLOG`)
- удаляется PID-файл

## L7-перехват HTTP/HTTPS

### `l7CaptureEnabled=false`

Главный выключатель L7-механизма (TLS SNI + HTTP Host + QUIC Initial SNI).

- `false` (по умолчанию) — поведение идентично релизам без L7: DNS-only мониторинг, `NFLOG`-правила не ставятся, netlink-сокет не открывается, kernel-модули `nfnetlink_log`/`xt_NFLOG`/`xt_connbytes` не загружаются, дополнительной CPU-нагрузки нет
- `true` — параллельно с DNS-каналом hrneo:
  1. резолвит WAN-интерфейс (см. `l7WanInterface`); при неудаче — L7 отключается, DNS-only
  2. загружает kernel-модули `nfnetlink_log` и `xt_NFLOG` через syscall `init_module` (пути `/lib/modules/$(uname -r)/*.ko`); **fallback отсутствует** — если модули недоступны, L7 полностью отключается с `[WARN]`, демон продолжает работу только на DNS-канале
  3. загружает `xt_connbytes` (если ещё не загружен)
  4. открывает `NFLOG`-сокет через `NETLINK_NETFILTER` на группе `l7NflogGroup`
  5. добавляет в `iptables`/`ip6tables` `mangle/FORWARD` и `mangle/OUTPUT` правила копирования первых 2..N пакетов TCP-потока (`dport 443` и `80`) в `NFLOG`-группу, при `l7EnableQUIC=true` — ещё UDP/443 длиной от 1200 байт (правила ставит коммитер netfilter в том же batch, что и `CONNMARK`)
  6. на каждую копию парсит TLS ClientHello (SNI), HTTP Host или QUIC Initial (SNI)
  7. при совпадении имени с watchlist — destination-IP попадает в соответствующий `ipset` так же, как DNS-ответ; дальше обычная цепочка `CONNMARK`/маршрутизации
  8. при **первом** добавлении этого IP (он был выпущен через WAN до попадания в ipset) и при `ConntrackFlush=true` hrneo точечно удаляет conntrack-запись триггернувшего соединения по 5-tuple — соединение реконнектится через политику, а не остаётся в обход неё до таймаута
- `NFLOG` — нетерминирующая цель: пакет только копируется и продолжает обычный путь, hrneo его не модифицирует. Это делает L7-канал совместимым с DPI-десинхронизаторами (zapret2 / nfqws2 / tpws), которые используют `NFQUEUE` на той же машине, — взаимного «голодания» по трафику нет (разбор — `CONFLICT_ZAPRET2.md`)
- разрыв триггернувшего соединения подчинён флагу `ConntrackFlush` (см. раздел «Conntrack»): при `ConntrackFlush=false` L7 не сбрасывает соединение, и трафик к хосту остаётся в обход политики до реконнекта приложением. Удаляется только триггернувшее соединение, точечно по 5-tuple, без полного DUMP таблицы
- закрывает «слепые зоны» DNS-only схемы: клиенты с DoH/DoT/DoQ, hardcoded-IP с TLS SNI, легаси-HTTP, QUIC/HTTP-3 (Safari/iCloud/h3)
- расшифровка DoH/DoT/DoQ/ECH невозможна (требует MITM) и не делается
- горячее переключение не поддерживается; смена флага требует `/opt/etc/init.d/S99hrneo restart`

### `l7NflogGroup=210`

Номер `NFLOG`-группы для L7-перехвата.

- пространство групп `NFLOG` отдельное от номеров `NFQUEUE` (общего конфликта с zapret/nfqws/tpws нет); при совпадении с другим потребителем NFLOG на этой же машине задать любое непересекающееся значение (диапазон `1..65535`)
- параметр строго положительный: `0` и отрицательные значения в конфиге → `[WARN] Invalid l7NflogGroup value: <значение>` и дефолт `210`, во флаге `--l7NflogGroup` — ошибка и выход 1. Группа `0` поэтому недоступна (её часто занимает штатный лог/ulogd)

### `l7EnableTLS=true`

Парсить TLS ClientHello на `dport 443`.

- `false` — копии пакетов порта 443 доходят до диспетчера и отбрасываются без вызова `tls_extract_sni` и без матчинга по watchlist; правило firewall при этом всё равно установлено (`NFLOG` лишь копирует пакет, сам трафик не затрагивается)
- имеет эффект только при `l7CaptureEnabled=true`

### `l7EnableHTTP=true`

Парсить HTTP Host на `dport 80`.

- `false` — пакеты порта 80 не анализируются (см. `l7EnableTLS`)
- имеет эффект только при `l7CaptureEnabled=true`

### `l7WanInterface=`

Имя WAN-интерфейса для firewall-правил L7.

- пусто (по умолчанию) — hrneo определяет автоматически по таблице маршрутизации: читает `/proc/net/route`, ищет строку с `Destination=00000000` (маршрут по умолчанию) и берёт имя интерфейса из колонки 0
- явное значение (например, `l7WanInterface=eth3`) — отключает автодетект и подставляется в правила как есть
- если интерфейс невозможно определить (ни конфиг, ни автодетект) — L7-перехват отключается с предупреждением `[WARN]`, DNS-канал продолжает работать

### `l7ConnbytesMax=8`

Верхняя граница окна `connbytes` для правила `dport 443`.

- правило:

  ```
  -m connbytes --connbytes-dir=original --connbytes-mode=packets --connbytes 2:N
  ```

- нижняя граница фиксирована (`2`) — пропускаем SYN, ловим со второго пакета
- для `dport 80` значение автоматически ужимается до `min(l7ConnbytesMax, 4)` — HTTP-запрос укладывается в первые пакеты, большее окно избыточно
- увеличение помогает при сильно фрагментированном TLS ClientHello (Kyber/MLKEM)

## Реассамблеция длинных ClientHello (TCP + QUIC)

Современные браузеры Chrome/Firefox при включённом post-quantum keyshare (X25519MLKEM768) отправляют ClientHello размером ~1.6–3.5 KB. TCP MSS обычно 1460 байт, поэтому ClientHello разрезается на 2–3 TCP-сегмента (а в QUIC — на 2+ Initial-датаграммы). SNI extension в первом сегменте/фрагменте обычно отсутствует — для его извлечения hrneo буферизует фрагменты в памяти до сборки полного ClientHello. Один пул `tcp_reasm` обслуживает оба источника: TCP-сегменты (по `seq`) и QUIC CRYPTO-фрагменты (по CRYPTO-offset); QUIC-ключи помечены `family|0x80` и не коллидируют с TCP.

### `l7TcpReasmEnabled=true`

Включить буферизацию неполных ClientHello (TCP **и** QUIC).

- `true` (по умолчанию) — для каждого TLS-соединения, у которого в первом полученном пакете `record_len > payload_len`, создаётся запись в хеш-таблице по 5-tuple (`saddr:sport:daddr:dport:family`). Последующие пакеты с правильным следующим TCP `seq` дописываются; при достижении `record_len` запускается `tls_extract_sni` на собранном буфере, и при совпадении с watchlist destination-IP попадает в `ipset` с тегом `[TLS-SNI]`. Аналогично собираются QUIC CRYPTO-фрагменты (тег `[QUIC-SNI]`)
- `false` — длинные ClientHello (Kyber/MLKEM) игнорируются на обоих каналах; fast-path для коротких CH (помещающихся в один TCP-сегмент / одну QUIC-датаграмму) продолжает работать. Можно использовать для regression-сравнения или экономии памяти на маломощных роутерах
- имеет эффект при `l7CaptureEnabled=true` и (`l7EnableTLS=true` для TCP / `l7EnableQUIC=true` для QUIC)
- **out-of-order TCP-сегменты** (`next seq > expected`): запись удаляется. На стабильных каналах client→server такое практически не встречается; out-of-order reasm с heap'ом отложен в подфазу 2.1
- **ретрансмиссии** (`seq < expected`): тихо игнорируются

### `l7TcpReasmMaxEntries=256`

Максимум одновременно буферизуемых соединений.

- допустимый диапазон `1..256` (`TCP_REASM_MAX_ENTRY`); общий лимит на TCP- и QUIC-записи (один пул)
- память: ~16 KB на запись (`TCP_REASM_BUF_SIZE`) + ~80 байт overhead. При `max=256` hrneo занимает дополнительно ~4 MB heap. При `max=64` — 1 MB
- при достижении лимита срабатывает LRU-eviction: удаляется самая старая запись по `ts_added`. Под нормальной нагрузкой (50–200 conn/s) eviction не должен происходить — это индикатор настройки слишком маленького `max` или нагрузки выше ожидаемой
- установка в `0` или отсутствие параметра — используется значение по умолчанию `256`

### `l7TcpReasmTtlSec=5`

TTL неполных записей в секундах.

- раз в секунду срабатывает `timerfd`, hrneo сканирует все buckets и удаляет записи старше TTL
- 5 сек с запасом покрывают типичный TLS handshake; больше не нужно, т.к. правило firewall пропускает только первые 2..8 пакетов flow
- частые удаления по TTL (недособранные ClientHello) — индикатор проблем сети (RTT, потери); в норме их быть почти не должно

## QUIC-перехват (UDP/443)

### `l7EnableQUIC=true`

Парсить QUIC Initial SNI на UDP `dport 443`.

- `true` (по умолчанию) — при `l7CaptureEnabled=true` hrneo устанавливает дополнительные правила NFLOG для UDP/443 с фильтром длины `--length 1200:` (QUIC Initial обязательно padded до ≥1200 байт по RFC 9000). Для каждого попавшего пакета запускается QUIC CRYPTO-walker (`probe_quic.c`):
  1. Проверка Long Header (`pkt[0] & 0xC0 == 0xC0`) и версии (v1: `0x00000001`, v2: `0x6b3343cf`)
  2. Определение Initial-типа: `(pkt[0] & 0x30) == 0x00` (v1) или `== 0x10` (v2)
  3. Извлечение DCID → вывод ключей через HKDF-Extract + 3× HKDF-Expand-Label
  4. Снятие Header Protection (AES-128-ECB) → расшифровка payload (AES-128-CTR)
  5. Frame walker с полным разбором ACK-фреймов → CRYPTO frame → SNI. Если ClientHello целиком лежит в CRYPTO-фрейме `offset==0` одного пакета — SNI извлекается сразу (fast-path без состояния). Если разбит на несколько Initial-датаграмм (пост-квантовый CH ~1.6–2 КБ, X25519MLKEM768/Kyber) — фрагменты собираются по CRYPTO-offset (см. ниже)
  6. Результат добавляется в watchlist-ipset с тегом `[QUIC-SNI]`
- `false` — UDP/443 не перехватывается; UDP NFLOG-правила не устанавливаются; `quic_extract_sni` не вызывается
- имеет эффект только при `l7CaptureEnabled=true`
- QUIC-соединения имеют conntrack-записи с `proto=17` (UDP); при `ConntrackFlush=true` и первом добавлении IP — точечный DELETE по 5-tuple UDP, как и для TCP

**Ключевые детали реализации:**

- **Соли:** QUIC v1 RFC 9001 `38762cf7f55934b34d179ae6a4c80cadccbb7f0a`, v2 RFC 9369 `0dede3def700a6db819381be6e269dcbf9bd2ed9`
- **Дешифровка:** AES-128-CTR, не GCM (верификация тега пропускается) — достаточно для извлечения SNI
- **ACK-frame skip:** в отличие от простых парсеров, hrneo полностью разбирает ACK(0x02)/ACK_ECN(0x03) через varint-поля, не прерываясь на них — позволяет найти CRYPTO-фрейм, идущий после ACK
- **Реассамблеция многодатаграммного Initial:** CRYPTO-фрагменты (`offset`, `data`, `len`) собираются в `l7_dispatch.c` поверх **того же** пула `tcp_reasm`, что и длинные TLS ClientHello — отдельного модуля и GC-таймера нет. `offset==0` → `tcp_reasm_start` (record_len = 4 + длина CH из handshake-заголовка), `offset>0` → `tcp_reasm_feed`; по завершении собранный CH → `tls_extract_sni`. QUIC-записи в общем пуле помечены `family|0x80` — не коллидируют с TCP. **Управляется тем же флагом `l7TcpReasmEnabled`** (см. раздел «TCP-реассамблеция»): при `false` работает только одно-датаграммный fast-path
- **Криптография:** pure-C SHA-256, HMAC, HKDF, AES-128 в `src/quic_crypto.c`; только целочисленные операции — работает на MIPS soft-float без аппаратного FPU

## Системные требования для `l7CaptureEnabled=true`

- `iptables`/`ip6tables` с поддержкой матчей `connbytes`, `length`, `tcp`, `udp` + target `NFLOG`
- kernel-модули `nfnetlink_log`, `xt_NFLOG` — на Keenetic присутствуют в `/lib/modules`, но не автозагружаются; hrneo подгружает сам через syscall `init_module` (порядок: `nfnetlink_log`, затем `xt_NFLOG`). Если их нет — L7 отключается **без fallback**, демон работает на DNS-канале
- kernel-модуль `xt_connbytes` — аналогично, hrneo подгружает сам через `init_module`
- демон запущен от root (доступ к `NETLINK_NETFILTER` для NFLOG и conntrack-DELETE, `AF_PACKET`, `init_module`)

## Примеры использования GeoSite в `domain.conf`

```

geosite:google/HydraRoute

geosite:google,geosite:netflix/HydraRoute

## GeoSite и обычные домены вместе, порядок не важен
geosite:google,youtube.com,youtu.be/HydraRoute
youtu.be,youtube.com,geosite:netflix/HydraRoute

youtube.com,youtu.be/HydraRoute

youtube.com/nwg0

youtube.com/awgm0

geosite:CATEGORY-ADS-ALL/Block
```
